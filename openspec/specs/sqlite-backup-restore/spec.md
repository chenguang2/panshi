# SQLite Backup Restore

## Purpose

换机/灾备场景下提供恢复向导：从远端备份包经临时目标输入、下载校验、高危确认后落位激活，使新机或受损机器恢复到备份时点数据；全程不热替换正在使用的数据库文件，旧库保留供手工回退，并提供等价的手工兜底恢复文档。

## Requirements

### Requirement: 临时目标输入的恢复入口
恢复向导 SHALL 支持两种备份来源：**从已配置位置选择**（列出全部已配置位置——含停用位置（标注停用）；提供「全部位置」聚合视图：对全部已配置位置（含停用）逐位置列包、**按包名去重合并**、行上标注存在位置；某位置不可达时标注该位置失败、不阻断整体列表；**无任何已配置位置时聚合返回空列表并提示改用手动输入，不报错**）或**手动输入**远端目标参数（主机、端口、用户、认证方式、密码或密钥、远端目录）；**包校验（下载校验步骤）与列包同构地支持位置引用：从已配置位置选择时 MUST 仅以位置引用发起，凭据由服务端解密注入（API 不回显明文，前端无法回传连接字段）；「全部位置」视图下选定包的校验 MUST 落到该包存在位置中的某一个具体位置执行**；恢复流程 MUST NOT 依赖已存备份配置（换机场景新机配置表为空，手动输入为默认路径）；备份任务进行中时恢复 MUST 被拒绝并提示（与备份共用互斥）。

#### Scenario: 新机空配置恢复
- **WHEN** 新机器部署同版本平台后（备份配置表为空）打开恢复向导
- **THEN** 向导默认手动输入路径，要求临时输入远端目标参数并可列出远端备份

#### Scenario: 已配置位置的包校验
- **WHEN** 用户在已配置位置或「全部位置」视图选定包并发起校验
- **THEN** 校验以位置引用（target_id）发起、凭据由服务端解密，「全部位置」时落到该包存在位置中的具体位置，校验通过后进入高危确认

#### Scenario: 从已配置位置选择
- **WHEN** 已配置备份位置的用户打开恢复向导选择「从已配置位置选择」
- **THEN** 位置下拉列出全部位置（停用位置标注停用），选中后列出该位置远端备份

#### Scenario: 全部位置聚合去重
- **WHEN** 用户选择「全部位置」聚合视图且同一包名存在于多个位置
- **THEN** 列表按包名去重合并、按时间戳倒序，行上标注该包存在的位置

#### Scenario: 位置不可达降级
- **WHEN** 聚合视图下某位置 SSH 不可达
- **THEN** 列表标注该位置失败，其余位置的包照常列出，流程不阻断

#### Scenario: 无已配置位置聚合空列表
- **WHEN** 新机无任何已配置位置时选择「全部位置」聚合视图
- **THEN** 返回空列表并提示改用手动输入，不报错

#### Scenario: 备份进行中拒绝恢复
- **WHEN** 定时或手动备份正在执行时用户发起恢复
- **THEN** 恢复被拒绝并提示等待备份完成

### Requirement: 远端备份列表与包内容明示
系统 SHALL 列出远端目录中的备份包（仅白名单文件名——与备份侧共用的组合正则，同时接受新格式 `panshi_backup_{source}_{时间戳}.tar.gz` 与升级前旧格式；忽略 .part 残留），**排序 MUST 按包名中解析出的备份时间戳倒序**（混合来源下文件名字典序不再等价于时间序）；列表 MUST 展示各包的**来源标识**（**文件名解析是唯一事实来源**，与备份侧排序/清理同源；旧格式包无来源标识时显示为未知；meta 的 source 字段仅作核对，与文件名解析不一致时标注包被改名过）与 meta 摘要（备份时间、app 版本标识、包体积、skipped 库清单、未包含的 B 类数据段）；新机版本标识与备份包可比较且低于备份包时 MUST 给出明确提示（不可比较时不提示、不阻断）；下载前 MUST 校验文件仍存在，已被清理则提示刷新列表。

#### Scenario: 列表展示与版本提示
- **WHEN** 用户输入可达的远端目标
- **THEN** 列出全部备份包及摘要；若版本可比且备份包版本高于本机，对应条目出现版本差异提示

#### Scenario: 新旧格式并存可见
- **WHEN** 远端目录同时存在升级前旧格式包与多台机器的新格式包
- **THEN** 列表全部展示，新格式条目各自显示来源标识，旧格式条目来源标识显示为未知

#### Scenario: 混合来源按时间排序
- **WHEN** 不同来源标识的包在时间上交错存在
- **THEN** 列表按各包文件名中的时间戳倒序排列，而非文件名字典序

#### Scenario: 包内缺失段明示
- **WHEN** 选定包备份时未勾选 task-logs 与 static
- **THEN** 列表/选包页明示「本包不含：static、task-logs」，以及 skipped 库清单（若有）

#### Scenario: 列表包已被清理
- **WHEN** 用户选择某包发起下载但该文件已被远端清理
- **THEN** 提示包不存在并建议刷新列表

### Requirement: 下载校验
系统 SHALL 将选定备份包下载到本地临时目录并执行校验：tar 完整性、逐文件 SHA256 与 meta.json 比对、每个数据库快照的 SQLite `PRAGMA integrity_check` 与关键表存在性；任一校验失败 MUST 拒绝落位并给出明确错误，且本地运行数据未被改动。

#### Scenario: 校验通过
- **WHEN** 选定包下载后所有校验项通过
- **THEN** 进入高危确认与落位激活流程

#### Scenario: 损坏包拒绝落位
- **WHEN** 包内任一文件 SHA256 与 meta.json 不符或某数据库快照 integrity_check 失败
- **THEN** 恢复终止并提示具体失败项，本地运行数据未被改动

### Requirement: 高危确认
恢复落位前向导 MUST 要求用户勾选「我了解恢复将覆盖本机数据库与配置文件」确认；未勾选时 MUST NOT 执行落位。

#### Scenario: 未确认阻止落位
- **WHEN** 用户未勾选高危确认即点击执行恢复
- **THEN** 落位不执行并提示需先确认

### Requirement: 落位与激活
校验与确认通过后，系统 SHALL 按以下顺序落位：**先落 key 文件**（.jwt_secret、.env.*，权限 600），再落库文件与配置/清单文件；恢复的数据库 SHALL 落为 `<原名>.restored-<时间戳>`（按 meta.json 记录的各库原路径对应落位），随后改 db_config 的 active 指针指向恢复的活动库并经**现有活动库切换机制（引擎重载）激活**——MUST NOT 热替换正在使用的数据库文件；切换 MUST 继承 database-management 既有需求「存在运行中任务时禁止切换」的语义；被替换的旧库文件 MUST 保留为 `.pre-restore-<时间戳>` 供手工回退；每次恢复前 MUST 清理历史遗留的 `.restored-*` 残留；恢复完成后界面 MUST 提示成功并工作在恢复后的数据上；**恢复的备份配置含来源标识时，完成提示 MUST 附带来源标识检查提醒（显示继承的标识值；共享目录双跑场景需人工修改，避免两机同标识互删）**；**恢复的备份配置含备份位置时，完成提示 MUST 附带位置可达性核对提醒（位置随包落位，新机未必可达）**。

#### Scenario: 恢复激活
- **WHEN** 校验与确认通过的包执行恢复
- **THEN** 恢复的库以 .restored 后缀落盘、active 指向它并经引擎重载激活，后续查询工作在恢复后的数据上，全程不出现对活动数据库文件的热替换

#### Scenario: 运行中任务阻止恢复
- **WHEN** 存在运行中任务（迁移等）时执行恢复落位
- **THEN** 恢复被阻止并提示，与数据库切换语义一致

#### Scenario: 旧库可回退
- **WHEN** 恢复完成
- **THEN** 原活动库文件保留为 .pre-restore-<时间戳>，可按文档手工回退

#### Scenario: 密钥文件先落且权限收紧
- **WHEN** 落位 .jwt_secret 与 .env.* 文件
- **THEN** 它们先于库文件落位、权限为 600，引擎重载后解密与连接使用包内自洽状态

#### Scenario: 清理历史 restored 残留
- **WHEN** 第二次执行恢复
- **THEN** 上次恢复产生的 .restored-* 残留被先行清理，不累积

#### Scenario: 恢复完成提示来源标识
- **WHEN** 恢复的备份包配置含来源标识且恢复成功完成
- **THEN** 完成提示显示继承的来源标识值，并提醒共享目录双跑场景需检查修改

#### Scenario: 恢复完成提示位置核对
- **WHEN** 恢复的备份配置含备份位置且恢复成功完成
- **THEN** 完成提示提醒核对已落位备份位置的可达性

### Requirement: 恢复审计
恢复操作（含校验失败终止、确认阻止）MUST 写操作审计日志，记录所选备份包与结果。

#### Scenario: 恢复成功审计
- **WHEN** 一次恢复成功完成
- **THEN** 审计日志记录恢复的备份包文件名与成功结果

### Requirement: 手工兜底路径
文档 SHALL 提供与向导等价的手工恢复命令（scp 拉包、解包、**按 meta.json 记录的原路径映射落位各库**、重启平台），供 UI 不可用时使用。

#### Scenario: 手工恢复可用
- **WHEN** 平台 UI 不可用但远端备份与同版本部署介质可达
- **THEN** 运维可按文档手工命令（含原路径映射与 .jwt_secret 权限收紧）完成等价恢复
