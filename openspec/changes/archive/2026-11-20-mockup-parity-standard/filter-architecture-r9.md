## 一、现状矩阵（5 个列表页 × 4 个维度）

| 页面 | 状态筛选形态 | 方法筛选 | 页头统计徽标 | 第二行 |
|---|---|---|---|---|
| 节点管理 | **下拉**（运行中/已停止/未检测） | — | 总数 + 运行中/已停止/未检测 | 无 |
| 路由管理 | **下拉**（已/待/未发布） | **下拉 + chips 行**（双入口） | 总数 + 已发布/待发布/未发布 | 方法 chips |
| 上游管理 | **无**（完全缺失） | — | 总数 + 已发布/待发布 | 无 |
| 四层代理 | **分段 tab 组**（含计数，全部/未发布/待发布/已发布） | — | 无 | 无 |
| DNS 代理（UDP） | **分段 tab 组**（同四层） | — | 无 | 无 |

四个维度各自都有 2–3 种做法 → 这就是用户感觉「不一致」的根源。

**先说一个事实**：用户问的「① 四层/DNS 要状态 chip 平铺」——**这两页已经是平铺 + 计数了**（`.sp-status-tab`：全部 19 / 未发布 8 / 待发布 2 / 已发布 9，29.5px 高、圆角 7px、选中实心 accent）。差别只在**造型**：它是一整个外框的分段控件，不是 `f-chip` 胶囊。所以 ① 的真实诉求应表述为「造型统一到 chips」，而非「新增平铺」。

## 二、四问逐条回答

### ② 路由 / 上游是否也该平铺状态

**应该，而且比方法更该。** 三条依据：

1. **值域小且固定**：发布三态（未发布/待发布/已发布）不需要搜索、不需要滚动 → 下拉是"隐藏式"控件，用户看不见有哪些选项，更看不见各自数量。
2. **频次高**：发布前核对「哪些还没发」是本系统最高频动作；而方法筛选用在多路由排障时，属低频。
3. **可承载计数**：chips 能带数字，下拉不能 —— 顺带解决第 ④ 问的"统计与筛选脱节"。
4. **上游现在是缺口**：页头写着「7 已发布 / 39 待发布」，但**没有任何状态筛选入口**（工具条只有分组/集群/算法）。补齐后上游才与其它页对齐。

### ③ 路由第二行改成状态 chips、方法保留下拉 —— 更合理

**是，这是本轮最正确的一条。** 理由是"频次与形态匹配"：

| 维度 | 状态（3 项，高频） | 方法（9 项，低频） |
|---|---|---|
| 形态 | chips 平铺 ✅ 一眼可见、带计数 | 下拉 ✅ 省宽度、不常驻 |
| 现状 | 下拉（**与频次不匹配**） | 下拉 + chips（**双入口，信息重复**） |
| 空间 | 355px（第二行，工具条不受影响） | 110px（工具条内） |

改造后：**每个筛选维度只有一处入口**，状态看得见数量，方法不占常驻宽度。实测工具条（1600 视口、卡片 1310）为：搜索 150 + 分组 104 + 集群 120 + 上游 104 + 插件 104 + 方法 104 + 右侧簇 429 ≈ **1175px**，余量 135px ✓；1366 视口会换行（可接受，且这正是 r8 已批准的 wrap 兜底）。

> ⚠️ **冲突提示**：这与你上一轮批准的 r8「方法 10 项全列 chips」互相排斥 —— 二者都合理但只能选一个。本文推荐 ③（方法回下拉、方法 chips 行取消），因为它同时让"方法双入口"和"工具条宽度"两个问题一起消失。

### ① 状态 chips 是否推广到四层 / DNS

**是，但只是统一造型**：把 `.sp-status-tab` 分段控件换成 `f-chip` 胶囊 + 计数后缀（视觉与路由/上游/节点完全同构）。信息量与位置不变，零功能变化。

### ④ 页头状态统计是否冗余

**是冗余，而且现在还「不准」。**

**冗余**：状态分布将在 chips 里带计数，页头再列一遍是同一组数字出现两次（且页头的不可点，chips 的可点）。

**不准（真实缺陷）**：路由页页头徽标的分布取自 `page_size=500` 的一次抽样，却按"总数"呈现。实测：

| 状态 | 页头徽标（500 抽样） | 真实全量（1596 条） | 偏差 |
|---|---|---|---|
| 未发布 | 331 | **1421** | **−1090** |
| 待发布 | 166 | 171 | −5 |
| 已发布 | 3 | 4 | −1 |

上游页 258 条（< 500）→ 抽样即全量，数值正确；四层/DNS 卡片页全量加载 → 正确。**只有路由页错**，但错得很离谱。

**建议**：页头只保留总数徽标（`1596 路由`），状态分布改由 chips 承担；chips 的计数必须来自**权威计数**（见下）。

## 三、技术前提：chips 计数需要「精确计数」

现状计数有三条来源，精度不同：

| 来源 | 精度 | 适用 |
|---|---|---|
| 卡片页全量加载（四层/DNS） | 精确 | 保持 |
| 列表 500 抽样（路由/上游页头徽标） | 路由页失真 | **不可用于 chips** |
| 后端聚合（`SELECT status, COUNT(*) GROUP BY`） | 精确 | 建议新增 |

**提案**：为分页列表页新增聚合计数端点（或给现有列表端点加 `with_stats=1` 返回 `{total, by_status}`），路由/上游/节点的 chips 计数一律走它；`page_size=500` 抽样副本随之废弃（顺带修掉第 ④ 问的数值缺陷）。

代价：后端 1 个端点 + 3 页接线 + 测试；风险低（纯读）。

## 四、三个方案

### 方案甲（推荐）· 状态 chips 行 + 方法下拉 + 页头只留总数

- 路由：工具条 5 下拉（分组/集群/上游/插件/**方法**）；第二行 = 状态 chips（带计数）；**取消方法 chips 行**。
- 上游：新增第二行 = 状态 chips（补上现在完全缺失的状态筛选）。
- 节点：新增第二行 = 运行态 chips（运行中/已停止/未检测[/已禁用]）。
- 四层/DNS：内联状态分段 → 换成同款 chips（同为一行，不新增行）。
- 页头：删除状态类徽标，只留总数。
- 后端：新增聚合计数（chips 与页头共用）。
- 效果：全站「状态 = 可见可点的 chips」「其它筛选 = 下拉」，每个维度单一入口，无重复计数。

### 方案乙 · 单行派（状态 chips 塞进工具条，不新增行）

- 省 41px 高度，但实测工具条自然宽 ≈1428px > 卡片 1310px（1600 视口即溢出），**右侧簇会被挤出视野**——与当前「平铺看不见」是同一个坑。除非再砍掉搜索框或某个筛选，否则不可行。

### 方案丙 · 双 chips 行（状态 + 方法都在第二行）

- 信息最全，工具条只留下拉；但方法与状态混行需要分隔与两个 label，整行 ≈1150px（1200 视口折行），且方法与状态仍是两类语义挤在一行。
- 若未来方法需要"常用常驻"，这是备选。

## 八、第十轮：状态行位置 与 页头统计//chips 的重复（2026-11-18 复核）

### 8.1 事实（真机 DOM 量测）

| 页面 | 卡片内顺序（实测） | 「总数」出现处 |
|---|---|---|
| 节点 | 工具条 → **批量条(42px)** → 状态 chips(41px) → 表格 → 分页 | **4 处**：工具栏「共 40 个节点」/ 页头「40 节点」/ chips「全部 40」/ 分页「共 40 个节点」 |
| 上游 | 工具条 → 状态 chips → 表格 → 分页 | **4 处**：工具栏「共 258 个上游」/ 页头「258 上游」/ chips「全部 258」/ 分页 |
| 路由 | 工具条 → 状态 chips → 表格 → 分页 | **3 处**：页头「1596 路由」/ chips「全部 1596」/ 分页（工具栏计数已 `showCount=false`） |

→ 三页**都已有独立的状态行**；差别只有节点页的「批量条」插在工具条与状态行之间（设计页 `nodes.html` 同序）。
→ 「总数」在节点/上游页被呈现 4 次，路由页 3 次 —— 用户感知的冗余成立，且比预期更重。

### 8.2 问题一：状态行该放在哪

- 现状（节点）：工具条 → 批量条 → 状态行。「批量条」是**操作面**（已选 0 项 / 批量启动…），「状态行」是**筛选面**；
  把操作面夹在筛选面之间，会让筛选控件与它筛选的表格之间多隔一条，且与上游/路由不同构（它们没有批量条）。
- 两种收口：
  - **A（推荐）**：工具条 → 状态 chips 行 → 批量条 → 表格。筛选面连续（工具条+状态行），操作面紧贴表格；三页同构（无批量条的页自然就是 工具条 → 状态行 → 表格）。
  - B：维持现状（工具条 → 批量条 → 状态行），设计页已是此序。

### 8.3 问题二：页头数量徽标是否冗余

是。但**不能只删一处**，要先把「总数」的职责分清：

| 位置 | 语义 | 建议 |
|---|---|---|
| 工具栏「共 N 个 X」 | 与页头/分页重复（路由页已关掉） | **删**（节点/上游对齐路由） |
| 页头「N 节点/上游/路由」 | 页面级总量身份（进页面一眼看规模） | **与 chips「全部 N」二选一** |
| chips「全部 N」 | 分布分母（与其它状态 chip 并列比较） | 倾向保留（删掉它，chips 行第一个会缺数字、与邻居不齐） |
| 分页条「共 N 条」 | **当前筛选命中数**（语义不同，且随筛选变化） | 保留 |

于是页头有两种处理：
- **甲（推荐）**：页头徽标改为**补充维度**（chips 无法表达、且非重复的信息）：
  - 节点 → 「5 集群」（当前筛选下的集群数，前端已有）
  - 上游 → 「312 目标」（目标节点总数，`statsUpstreams` 已含 targets）
  - 路由 → 「12 上游」（涉及的不同上游数；需在 `/routes/status-counts` 增加 `COUNT(DISTINCT upstream_id)`）
  - 好处：页头提供"规模/依赖"信息，chips 提供"分布"，分页提供"命中"，三处各司其职。
- 乙：**删掉页头徽标**，页头只剩标题 + 描述 + 主按钮（零后端；视觉更清爽，但失去"一眼看规模"）。
- 丙：页头保留总量作为**唯一**总量，chips 的「全部」去掉数字后缀（零后端；但 chips 行不再有分母）。

## 十一、卡片页是否引入「集群分组 + 分组/平铺」（参照 `Z:/Live-Artifact-5/proposal-c`，2026-11-18）

### 11.1 参照版本做了什么（实测该目录文件）

- 工具条：`全部集群分组` + `全部集群` + `.seg`（分组 | 平铺）；
- **分组模式**：每个集群一条 `.cg-band`（跨 3 列，左侧 3px 色条 = 该集群色相，含集群名 + 分组徽标 +
  `N 插件组 / 2 已发布 / 1 待发布 / 1 未发布` 四枚 g-chip + 折叠按钮），卡片按集群分堆；
- **平铺模式**：`.cg-band { display:none }`，卡片左缘 4px 集群色条 + 卡头 `.rc-top` 显示「集群 + 分组」；
  分组模式下 `.rc-top` 隐藏（信息不重复）；
- 卡片 426×**215px**、3 列（`minmax(340px,1fr)`），折叠状态由 `data-fold` 维护。

### 11.2 我方现状（10 页卡片设计稿 + 实现）

- 9/10 页（除插件开关）**已有**集群筛选、集群分组筛选、卡片上的集群/分组徽标；
- 卡片 415×**180px** 上限、3 列、状态由顶部 chips 行 + 卡内 `.ps-tag` 承担；
- 页头徽标已改「补充维度」，总数只在 chips「全部 N」与分页条各出现一次（约定 #86）。

### 11.3 数据量（决定性价比的关键）

| 页面 | 条目数（本库实测） | 3 列下高度 |
|---|---|---|
| 静态资源 | 6 | 2 行 |
| 全局规则 | 12 | 4 行 |
| 服务器证书 | 19 | 7 行 |
| 插件组 | 20 | 7 行 |
| 四层代理 | 32 | 11 行 |

→ 除四层代理（32）外，其余页面滚动 2–7 行即可看完；「折叠」的收益主要体现在 20+ 条的三页。

### 11.4 引入的收益

1. **按集群巡检**：band 一眼给出「该集群有几条、发布情况」，跨集群缺配置一目了然；
2. **心智统一**：与节点/上游/路由三页的「分组 | 平铺」完全同构，用户不必为卡片页另学一套；
3. **长列表收敛**：折叠后 32 条四层代理可以只展开目标集群。

### 11.5 引入的代价与冲突（必须先解决，否则是退化）

| # | 问题 | 说明 | 处理建议 |
|---|---|---|---|
| 1 | **状态计数第三次重复** | band 里的 `2 已发布 / 1 待发布` 与状态 chips 行重复 | band **只留「N 个X」**，状态分布交给 chips 行（约定 #86） |
| 2 | **分页与分组冲突** | 分组模式若分页，组被页边界切断、band 重复出现 | 分组模式**一次全量、隐藏分页**（最大 32 条，完全可行）；平铺模式保留分页 |
| 3 | **卡片高度** | 参照版 215px（多了 `.rc-top` 与副标题两行） | 分组模式隐藏 `.rc-top`、平铺模式显示集群角标；两模式都守 ≤180px |
| 4 | **集群色相系统** | 参照版每集群一色（`--gc`），跨页必须稳定 | 定 `cluster_id → hue` 固定映射（写进 theme.css 的 `.cluster-c1..c8`），不随机 |
| 5 | **无集群维度的页面** | 插件开关是全局开关；CA 根证书为平台级 | 这两页**不提供**分组/平铺（菜单置灰或隐藏 seg） |
| 6 | **批量模式叠加** | 卡片批量选择 + 分组折叠 + band 全选 | 需要「band 级全选」语义，参照版已有 `band-select`，可复用列表页的 `useListClusterGrouping` 思路 |

### 11.6 三个方案

- **方案 A（推荐，精简版）**：只给「集群维度 + 条目 ≥12」的 6 页加（插件组 / 全局规则 / 服务器证书 / 四层代理 / DNS-UDP / DNS-HTTP），并按 11.5 裁剪：band 不带状态计数、分组模式不分页、两模式都 ≤180px、集群色相固定映射。
- **方案 B（最小）**：不加分组/平铺，维持现稿（集群筛选下拉 + 卡片集群徽标）。零开发成本，但长列表（四层代理 32）仍需长滚，且与列表页交互不一致。
- **方案 C（照搬参照版）**：9 页全加，band 带状态计数、卡片 215px。**与刚统一的「总数只出现两次」「状态只归 chips」规则冲突，不推荐**。

### 11.7 样张结论与裁决（2026-11-18）

样张：`docs/ui/Live-Artifact-5/proposal-c/stream-proxies-grouping.html`（未改动 `stream-proxies.html`）。

**实测（我自己跑 Playwright 复验，非仅依赖 designer 汇报）**：

| 项 | 分组模式 | 平铺模式 |
|---|---|---|
| 分页条 | 0（全量 24） | **0（同样全量 24）** |
| 卡片最高 | 178.84px | 178.72px |
| 集群标识 | band（3×38px，「生产集群 · 生产环境 · 10 个四层代理 · 目标 12 个」） | 卡顶 22px 集群条 + 左缘 4px 色条 |
| 状态 chips | 全部 24 / 未发布 5 / 待发布 2 / 已发布 17（= 5+2+17 自洽） | 同左 |
| 折叠 | 整条 band 可点 + chevron，`aria-expanded` 双向同步；「全部收起」→ 0 可见、3 条 band 保留；「全部展开」→ 24 | 折叠按钮自动隐藏 |

**用户裁决**：① 集群分组 + 分组/平铺 采纳；② band 只留规模（不放状态计数）；③ 插件开关 / CA 根证书 隐藏该开关；④ **卡片页一律不分页**（两模式全量，总数只由 chips「全部 N」承担）；⑤ 默认「分组」；⑥ 批量管理必须可交互（样张已实现）。推广页面范围待定（建议 5 页：插件组 / 全局规则 / 服务器证书 / DNS-UDP / DNS-HTTP）。

**实现侧注意**：① 不分页 → 列表接口需一次取全量（建议 `all=true` 或 page_size 上限；破百条改虚拟滚动而非恢复分页）；② chips 计数仍走聚合端点，别依赖全量数组前端数（将来加分页不用重拆）；③ 批量删除弹窗须列出「平台配置 + Edge 已发布规则」两件事（#81 危险项解释）；④ 卡片页 batchbar 按需出现（`.batchbar-dynamic`）与列表页恒显的 batchbar 类名隔离，勿合并。
