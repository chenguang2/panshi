# Proposal: ssl-cert-rollback-consistency

## 背景

2026-10-23 用户排查「uapm 证书卡片/编辑里没有 IP 信息」时发现：证书的匹配名单（`sni` 字段）与证书本体 SAN 脱节。审计还原成因——用户对证书执行了两次回滚，回滚恢复逻辑把 7 月老版本的窄 `sni` 写回证书记录，而证书本体 PEM 保持今天新生成的内容，造成「节点证书里有 IP、平台匹配名单里没有」。

## 根因（两层）

1. **键名不对称**：SSL 版本快照即发布 `config_data`。当前发布格式按 SNI 数量二选一写 `sni`（单个）或 `snis`（多个），更老的 7 月格式写 `sni` 字符串。而回滚恢复 `_restore` 只认 `if "sni" in cfg`（`cluster_ssl.py:519`）——回滚到多 SNI 版本（`snis` 键）时匹配名单**静默不恢复**，回滚到老版本时又被老值整体覆盖。
2. **缺一致不变式**：`sni`（Edge 匹配名单）与证书本体 SAN 是两个独立存储，生成时同步一次（`sni_str = ",".join(cert_dns + cert_ip)`），此后回滚/更新都可能把二者掰开，且无任何检测或自愈。

## 影响的缺陷场景

- 回滚到多 SNI 版本 → sni 静默保持旧值 → 重新发布后 Edge 匹配名单与证书 SAN 不一致（域名匹配不上证书）。
- 回滚到老格式版本 → 老窄 sni 覆盖新全量 SAN sni（uapm 实况）。
- 存量已脱节的证书（如 uapm）无任何警示，用户无从知晓 Edge 匹配名单缺域名。

## 拟议变更

1. 回滚恢复键名双读兼容（`snis` 数组 / `sni` 字符串）。
2. 回滚后以**恢复的证书 PEM** 为唯一事实源重同步 `sni`（SAN 解析 → sni），消除部分恢复脱节。
3. 发布时 sni_list 从证书 PEM SAN 解析（解析失败回退现值）——存量脱节证书在下次发布时自愈，Edge 永远收到与证书一致的匹配名单。
4. 服务器证书卡片在 sni 与 SAN 不一致时显示警示 + 一键同步（存量数据可视化修复入口）。

## 影响

- **后端**：`cluster_ssl.py` 的 `_restore` 与 publish 的 `sni_list` 推导；零 schema 变更、零新列、零迁移。
- **前端**：`SslCertCard` 增加不一致警示行与同步按钮；`ServerCertList` 接线同步动作。
- **不改动**：版本快照存储格式（历史版本原样保留，读取侧兼容）；`VersionManagementModal` 通用确认流程。
