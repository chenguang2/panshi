# db-backup-dr-ux-optimization 设计

## 决策

### D1 恢复响应契约修复 = 端点透传（P0，问题 1）
`db_backup.py` 恢复执行端点现仅手工挑选 5 字段返回，丢弃服务层 `db_restore_service` 已返回的 6 个 D6 字段（schema_reconciled/tables_added/columns_added/key_changed/restart_recommended/schema_migration_error）→ 完成页两段安全提示永不显示（主规格「恢复完成指引闭环」早已要求展示，属实现违规）。修法：端点改为透传服务层返回的完整载荷（键集合以服务层为准，不在此处二次裁剪），前端 `types/dbBackup.ts` 恢复结果类型已声明这些字段（无需改前端消费逻辑）。备选「前端另调查询接口取完成态」被否：引入额外往返与状态同步复杂度，且服务层数据本就在手。
守卫：后端测试断言响应体含全部 11 个键（人为从服务层删一个键 → 测试红，反向验证有效性，沿用迁移域 pg-dialect 冒烟模式）。

### D2 全部位置推送失败的反馈 = 200 结构化（P0，问题 2）
现状链路：`db_backup_service` 把 failed 收敛为 raise → 端点 409 → 前端 catch 只 toast。双重病灶：① 失败结果与「任务冲突」共用 409（语义混淆，前端无法区分）；② 失败拿不到结构化载荷（分位置结果在服务层手里却进不了响应体）。修法：构建成功但推送全败/部分失败一律 **HTTP 200**，响应体携带与 success/partial 同构的结构化结果（status=failed + 逐位置子结果），前端复用既有 `runResult` 结构化弹窗（弹窗已支持三态渲染基础，补 failed 态）；409 保留给「已有任务进行中」冲突。部分成功（partial）现状已是 200——本决策使三态反馈路径归一。
连带：常驻错误条保留为持久入口（服务端 detail 兜底），双入口不冲突。

### D3 「立即备份」0 位置禁用（P0，问题 3）
`runDisabled` 增加 `enabledTargetCount === 0` 条件，tooltip/旁注「请先添加并启用备份位置」。后端 422 兜底保留（防御纵深，文案不动）。

### D4 「从未备份」文案拆分（P0，问题 10 关联）
统计格只留「从未备份」（muted），行动建议移入既有 `statusHint` 行（该行语义即「当前阻碍」，通道已存在）。

### D5 脏配置路由守卫 = `onBeforeRouteLeave`（P1，问题 4）
`DbBackupCard`（或薄壳 `BackupManagement.vue`）注册 `onBeforeRouteLeave`，dirty 时复用既有刷新确认弹窗语义（showOverlayModal，文案同 M6：说明将丢弃未保存修改）。`beforeunload` 不加（后台管理系统非表单站，避免关页误拦；与迁移域现状一致）。

### D6 全败包「恢复此包」屏蔽（P1，问题 5）
历史行 v-if 从 `package_name && targets.length` 收紧为「存在至少一个推送成功的子结果」（构建失败无子结果行时同样不可用）；不可用时不渲染按钮、以 muted 说明「该备份包未成功推送到任何备份位置」替代（行内失败原因展开保留）。向导侧预选 miss 的静默兜底保持（防御纵深）。

### D7 SSH 错误中文归因（P1，问题 7）
归因映射放**服务层**（`db_backup_service` 错误构建处）：按 errno/输出关键词分类（Connection refused / Authentication failed / could not resolve / timed out / No such file or directory / disk space / sshpass），首句中文归因含 host:port 与「请检查」建议，原始错误串完整保留在 detail 字段；前端无需改动四处展示点（首句自然上屏），仅在错误条展开区确保 pre-wrap 呈现原文（已具备）。备选「前端正则翻译」被否：分类知识在服务层（errno/输出语义），前端二次解析脆弱。

### D8 失败红点桥接 + 调度暂停提示（P1）
红点：`lastStatus === 'failed'` 时「备份历史」Tab 标签渲染红点；清除时机 = 查看过失败展开原因或下一次备份成功（前者实现为本地已读标记，后者随 status 刷新自然消失）。
调度暂停：status 载荷新增 `suspended_reason`（迁移运行中时填充「数据库迁移进行中」），前端「定时调度」格染黄 + 提示文案；不适用（无 SQLite/无启用位置）语义不变。

### D9 「最近推送」列拆分（P1，问题 12）
列头语义收窄为推送健康：健康点 + 相对时间（tooltip 详情）；手动测试结果改为行下展开区（复用既有行展开机制）。不做定时探活（P2）。

### D10 历史筛选上限披露（P1，问题 6）
筛选区常驻半句「仅筛选最近 200 条」（上限常量单点定义）；不扩池（后端分页与池化的取舍属性能域，本轮不动）。

### D11 历史直达自动校验（P1，交互优化）
预选命中且列包成功后自动 `doVerify`（与手动校验同路径、同来源标注）；仅历史直达路径触发（query/props 标记），手动进入不自动校验。安全闸（勾选确认 + 执行确认）不减。

### D12 历史清理（ADDED capability）
端点：`POST /db-backup/history/cleanup`（body: `{keep_last?: int, purge_all?: bool}` 二选一校验；挂 `db_backup` 权限；审计 detail 记录条件与删除条数）；服务层单事务删除主表 + 子结果。前端：历史工具行「清理历史」按钮 → showOverlayModal 确认（展示总数/将删条数/不可恢复/远端包不受影响）。安全守卫测试补采样。评审残留的测试失败记录由此清掉。

### D13 文案修正（P0/P1 顺带）
「搁浅语义」→「远端已推送的备份包将原样保留、不再自动滚动清理；如不再需要请登录备份机手工删除」；开关旁文案改状态语序（「定时备份未启用/已启用」）。均为既有需求的呈现细节，不入 spec。

## 影响面与风险

- 恢复执行端点响应结构扩展：向后兼容（纯新增字段），前端类型已声明；风险低。
- 立即备份 409→200 语义变更：**破坏性变更面 = 仅前端自身**（同仓库同发布），外部无 API 消费方（内部系统）；前端 catch 分支同步改造，测试覆盖三态。
- 调度 suspended_reason：status 载荷新增可选键，旧前端忽略不报错。
- 历史清理：物理删除不可逆，靠确认弹窗 + 审计兜底；不加软删除（历史表非业务数据，ROI 为负）。
