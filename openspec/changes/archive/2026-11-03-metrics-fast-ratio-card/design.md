# metrics-fast-ratio-card 设计

## Context

用户裁决（2026-11-02）：P95/P99 分位卡不做，改做「快速响应占比」精确占比卡；核心流量采用 3 列布局。

用户追加裁决（2026-11-03）：累计口径在本环境饱和（≥20ms 恒 100.00%，区分度为零），**再增加一个显示各个桶的值**——按桶区间自身占比呈现（如「10 < 耗时 ≤ 20 ms」的请求占多少），与累计口径互补。D1 段落预留的「见 D9」即此扩展（D9–D12）。

实测依据（2026-11-02 ClickHouse，`edge_http_latency` @ `otel_metrics_histogram`，`type=request`，1h 窗口 13:10→14:09）：

| 项 | 值 |
|---|---|
| `ExplicitBounds` | `[10, 20, 50, 100, 200, 500, 1000, 2000, 5000, 10000]` ms（5 种 latency_type 完全一致，11 桶） |
| ΔCount / ΔSum | 2,204,476 / 1,929,198 → 平均 **0.875 ms** |
| 桶增量 | `[2203696, 624, 154, 2, 0, 0, 0, 0, 0, 0, 0]` |
| `BucketCounts[1] / Count` | 6,291,981 / 6,293,590 = **99.97%**（≤10 ms） |
| `arraySum(BucketCounts)` | 恒等于 `Count`（桶计数完备，可作分母校验） |
| Prometheus 式插值 | P50 **5.00** / P95 **9.50** / P99 **9.90** / P99.9 9.99 ms（全部被首桶桶宽支配） |
| `edge_http_latency_max` (gauge) | 进程**累计**最大：03:00–10:00 恒 22 → 10:00 抬到 60 后持续 5 小时恒定，不可作「当前最大」 |
| `edge_http_latency_min` (gauge) | 恒 0（采集端未填） |
| `otel_metrics_exponential_histogram` | 0 行（无更细指数桶可退） |

`BucketCounts` 为 1-based 数组：`BucketCounts[i]` = 落在 `(ExplicitBounds[i-1], ExplicitBounds[i]]` 的请求数，故 `BucketCounts[1]` 正是「≤ 10 ms」。

## Goals / Non-Goals

**Goals**：总览页可观察尾部时延的**精确**信号（≤10ms 占比）；接入既有刷新/筛选/三态机体系；口径诚实（精确计数占比 + 阈值显式标注 + 阈值动态来源）。
**Non-Goals**：P95/P99 插值分位；区间分布的**时间序列形态**（11 条曲线不可读，2026-11-03 裁决为窗口聚合，见 D9）；采集端桶边界调整；按 latency_type 切换器（`request` 固定）。（原 Non-Goal「延迟分布条形卡（11 桶全貌）」已按用户裁决 2026-11-03 以 chip 分布形式纳入范围，见 D10——非比例条形图，规避饱和失真。）

## Decisions

### D1 口径：精确跑和占比，零插值

`fast_ratio = ΣΔ(前 k 桶前缀和) / ΣΔCount`，输出百分比，k = 阈值在 `ExplicitBounds` 中的 1-based 下标。分子分母都来自 bucket 计数增量，**不引入任何桶内分布假设**——这是与 P95/P99 的根本区别：占比在桶边界上是精确可数的，分位点在桶内是不可知的。

**⚠️ 2026-11-02 用户实测事故与纠正（必须遵守）**：`BucketCounts` 是**逐桶非累计**计数（`BucketCounts[1]` = (0,10] 的数量 99.97%、`[2]` = (10,20] 的 0.0217%…，全桶之和恰等于 `Count`）。初版写成 `BucketCounts[k]` **取单格**，于是只有首边界（k=1）碰巧正确：用户实测 10ms=99.96% 而 50ms=0.01%（后者只统计了 (20,50] 这一格）。正确写法 = 前缀和 `arraySum(arraySlice(BucketCounts, 1, k))`，保证阈值越高占比单调不减（当前数据：10ms 99.97% / 20ms 99.9961% / 50ms 99.9998% / 100ms 100%）。守卫：`test_threshold_prefix_is_monotone_by_bucket` + `test_threshold_50_uses_first_three_buckets`。

**该事故暴露的显示层问题（见 D9）**：累计口径在本环境饱和（≥20ms 恒 100.00%），区分度为零——这正是用户提出按桶展示的原因。

`Δ` 口径与平均耗时卡（D1 of metrics-avg-latency-card）同构：按 `Attributes` 分组取 `argMax(..., TimeUnix)` → `lagInFrame` 差分（首桶默认取自身 → 增量 0）→ 负增量（计数器重启）钳 0 → 跨序列求和后相除。多节点/多序列安全。

### D2 阈值动态取值，不硬编码 10ms

阈值 = 窗口内最新的 `ExplicitBounds[1]`（`argMax(ExplicitBounds[1], TimeUnix)`），随响应以 `threshold_ms` 返回，前端渲染进标题旁口径标注。理由：桶边界由 Edge 产品侧定义（本仓库无控制点），硬编码 10 会让卡片在边界变更后**静默失真**（数值含义变了、文案还写着 10ms）。若查询无行或数组取不到值 → 回退 10.0 并保持文案可用。

### D3 无请求桶不出点，而不是给 0%

平均耗时卡在 `ΔCount=0` 的桶给 `0.0 ms`（事实语义「没有请求被处理」）。占比卡**不能**照搬：0% 会被读成「全部请求都很慢」，与事实相反。因此 `ΔCount=0` 的桶**不输出该点**（sparkline 不落点，时间轴自然跨过），头部值取最近一个有效桶；窗口内一个有效桶都没有 → 空态「暂无上报数据」。同时这也自然丢弃了 lagInFrame 造成的首桶 0 增量点。

### D4 专用函数 + 专用端点（而非复用 avg-latency）

与 metrics-avg-latency-card D2 同理由：histogram 占比语义特异。新增 `query_fast_ratio_series(metric_name, since, interval, latency_type='request', bucket_index=1, ips=None) -> {"points": [...], "threshold_ms": float}`，端点 `GET /metrics/fast-ratio` 在既有 `_filter_response` 信封上追加 `threshold_ms` 兄弟字段（`data` 保持数组，不改变其他端点契约）。

### D5 布局：核心流量 3 列（用户裁决）

`核心流量` section 加类 `core-grid`：`grid-template-columns: repeat(3, 1fr)`；第一行 `QPS | 平均耗时 | 快速响应占比`，第二行连接状态 `span-full`。中宽屏（801–1180px，侧边栏占位后内容区不足以容纳三张可读卡片）降为 2 列 + 占比卡整行（`:nth-child(3) { grid-column: 1 / -1 }`），保持「无空网格格」；`@media (max-width: 800px)` 既有断点仍收敛为单列。其余三区网格不变。

### D7 阈值控件形态：下拉（用户裁决 B2）

阈值**只能是桶边界**：桶是区间计数，桶内任意点（如 30ms）不可精确得知，给任意值就只剩插值或区间显示两条路——前者正是本次否掉 P95/P99 的原因，后者总览页无人看。故控件为 `a-select`（`MetricChartCard` 新增 `header-extra` 插槽承载），选项来自接口 `bounds`（= `ExplicitBounds`），非边界值 API 返回 400 中文。默认首边界（当前 10ms）。切换只重发该卡（`setFastRatioThreshold` → `loadSingleChart`），不触发整页刷新；不持久化（与时间范围一致）。

### D8 实机发现的两处显示修正

- **单点显形**：窗口内只有一个有效桶时（无流量时段后的最后一分钟、采集端停更），折线无点可画 → 卡片头部有值但图区全空，看着像坏了。`MetricChartCard` 改为 `showSymbol: data.length === 1`（多点仍保持无符号 sparkline 惯例）。
- **数值与单位不拆行**：窄卡时 `99.93` 与 `%` 会被 flex 换行拆到两行；头部数值/单位收进 `.chart-number`（`inline-flex` + `nowrap`）。

### D6 数值格式与量程

`unit: '%'`，`MetricChartCard.formatMetricValue` 增加 `%` 分支（`toFixed(2)`，如 `99.97`），头部渲染 `99.97%`。sparkline **保持自动量程**（不锁 0–100）：锁死后健康态恒贴顶，劣化时 99.9→95 的跌幅几乎不可见；头部数值提供绝对值，趋势图负责呈现相对变化。

### D9 区间分布口径：与 D1 同源的逐桶精确占比（2026-11-03 扩展）

窗口聚合（非时间序列），对每个桶下标 i（1..N，N = len(bounds) + 1，末桶为溢出桶 `(bounds[-1], +∞)`）：

```
counts_i = Σ_序列 Σ_时段 ΔBucketCounts[i]      （逐元素差分、负增量钳 0）
total    = Σ ΔCount
ratio_i  = counts_i / total × 100             （两位小数）
```

差分语义与 D1 完全同构：按 `Attributes` 分组取 `argMax(BucketCounts, TimeUnix)` 数组 → `lagInFrame` 逐元素差分（PARTITION BY Attributes，首时段默认取自身 → 增量 0）→ 负增量（计数器重启）钳 0 → 跨序列求和。既有守卫（假成功钳 0、多序列分区）天然继承，不重写。零插值原则不变：分布只回答「落在哪个桶」，不假设桶内形状。

- 实现形态：逐元素数组差分 `arrayMap((f, p) -> greatest(f - p, 0), f_arr, f_prev)`（`f_prev` 来自独立内层的 `lagInFrame(f_arr, 1, f_arr)`），再 `ARRAY JOIN` 透视成行后 `GROUP BY idx` 求和；数组长度不齐（窗口内采集端边界变更，实测极罕见）按最短截断对齐，新增桶当段不计增量。
- `total ≤ 0`（窗口无请求）→ 返回 `bucket_stats = null`（与 D3 同语义：不显示全 0 分布）。
- 载体：`GET /metrics/fast-ratio` 响应追加 `bucket_stats` 兄弟字段（`{bounds, ratios, counts, total} | null`），**不新增端点**。分布与阈值无关（阈值只影响累计前缀），阈值切换重发属幂等冗余，接受——换取单一请求单一数据流。
- 与累计口径交叉验证（实机验收项）：`Σ ratios[1..k]` ≈ 阈值 `bounds[k-1]` 的累计占比（舍入容差内一致；≤10ms chip 应与头部值 99.9x% 同源）。

### D10 展示形态：区间 chip 列表（比例条被否）

**被否方案**：
- **比例分段条**（段宽 ∝ 占比）：实测分布 `[2203696, 624, 154, 2, 0×7]` 跨 6 个数量级，首桶 99.97% 吃满全宽、其余 10 桶千分位宽度——可视化失效。
- **对数宽度/对数色阶**：对占比取对数是伪可视化（0.03% 与 0.00%、99.97% 与 100% 视觉无差），误导性比没有图更强。
- **11 行表格**：信息最精确，但 3 列卡片区垂直膨胀约 +260px，不可接受。

**采用：水平 wrap 的 chip 列表**——每桶一枚：色点（按桶序绿→红插值，标识区间次序）+ 区间标签 + 占比两位小数（如 `10–20ms 0.03%`）。全 11 桶**无条件渲染**（0.00% 桶置灰），行数稳定不跳动（对齐 AGENTS #54 行高一致精神）；绝对计数与窗口总量放悬停（`10–20ms：624 次（0.03%）`，口径提示附「窗口内共 N 次请求」），chip 主值保持占比——用户诉求即「知道某区间占比多少」。区间语义左开右闭，由口径提示显式说明（文案表 #11）。

### D11 位置：核心流量行下全宽分布条（用户裁决 B，2026-11-03）

- **B（推荐）**：`core-grid` 行下追加全宽分布条（核心流量 section 内、连接状态卡之上）：标题「耗时区间分布」+ info 口径提示 + chips。理由：11 枚 chip 需要横向空间（1/3 卡宽要折 3–4 行）；**不改共享卡组件**（`MetricChartCard` 无需新插槽，规避 #217 消费方普查与断言反转）；801–1180px 断点下占比卡本就整行，分布条紧贴其下语义连贯。
- **A（备选）**：占比卡内图下方——需要 `MetricChartCard` 新增 bottom 插槽（共享组件变更，须先做消费方普查 + 断言反转清单，#217）；代价：同行三卡被撑高约 +60–90px，QPS/平均耗时卡底部留白。
- **C（被否）**：独立卡进网格——打破「无空网格格」（3 列排 4 卡）。

### D12 数据流：随 fast_ratio 卡单一请求

`bucket_stats` 由 `loadSingleChart('fast_ratio')` 同一响应解包写入 store（`fastRatioBuckets`）；时间范围/集群筛选/手动刷新/单卡重试同源更新。渲染纯数据驱动：`fastRatioBuckets == null`（加载中/出错/无请求）时分布条整块不渲染，不设独立三态——卡本体已承载三态机，分布条只是同一数据的第二视图。

### D13 头部值口径对齐窗口聚合（2026-11-03 用户实测反馈）

**现象**：头部「近 1 小时 100.00%」与分布条首枚 chip「≤10ms 99.98%」不一致——头部取**最近一个有效桶**的区间占比（该 5 分钟恰全为 ≤10ms → 100%），分布条是**全窗口聚合**（更早时段有 196 笔落在 10–20ms → 99.98%）。两个同标「≤10ms 占比」的数字并存必被误读（用户实测实锤），且 scopeLabel「近 1 小时」对「最近一桶」的头部值本就是错标。

**裁决（用户 2026-11-03：两者必须一致）**：头部值改为**窗口聚合占比** `window_ratio = ΣΔ(前 k 桶) / ΣΔCount × 100`（k = 阈值下标），与分布条同源同义；阈值=首边界时严格等于首枚 chip 值（原始计数相除后单次舍入，无逐桶舍入漂移）。

- sparkline 保持逐桶时间序列（趋势与悬停看单桶），头部是窗口汇总——「大数 = 窗口汇总、折线 = 趋势」为仪表盘标准形态；**D3 的「头部值取最近一个有效桶」就此废止**：窗口无请求时本就无点，`window_ratio = null` → 头部 `--`。
- 实现：`query_fast_ratio_series` 聚合既有行的 `f_total/c_total`（零新增 SQL），响应追加 `window_ratio` 兄弟字段；前端经 store `fastRatioWindowRatio` 传入 `MetricChartCard` 新可选 prop `headValue`（null/缺省走原 `latestValue` 逻辑，既有消费方零影响；#217 消费方普查：仅 MetricsDashboard 一处消费）。
- **平均耗时卡同改（用户裁决 2026-11-03）**：头部值同改为窗口聚合均值 `ΣΔSum / ΣΔCount`（全窗口单次舍入，响应 `window_avg_ms` 兄弟字段），复用 `headValue` prop（零新共享组件改动）；sparkline 逐桶趋势与「无增量桶 0.0ms」语义不变。「头部大数 = 窗口汇总、折线 = 趋势」自此为两张 histogram 卡的统一约定。

## Risks / Trade-offs

- **阈值与语义耦合**：卡片数值含义随桶边界变化（当前是 ≤10ms，边界若改为亚毫秒则自动变成 ≤0.5ms）。这是**有意**的（D2）：数值与标注始终一致；代价是跨时间比较需注意边界变更时点。已在口径标注中显式写出阈值。
- **健康态数值恒贴 99.9x%**：单看绝对值信息量低——其价值在「会掉」。若后续认为需要更强的头部信号，可加阈值告警色（如 <95% 变黄），本次不做。
- **无法回答「P99 多少毫秒」**：这是采集端桶粒度的硬限制，不是平台实现问题。若 Edge 侧将来提供亚毫秒桶，可在本卡旁补真分位卡（届时本卡仍保留：精确占比与分位互补）。
- **多序列聚合语义**：占比按序列求和后再相除（分子分母同源），跨节点加权正确；不会像对「各节点占比求平均」那样偏离。
- **分布与累计的舍入尾差**：ratios 逐桶独立两位舍入，chips 合计可能 ≠ 100.00%；展示层不做重归一化（重归一会破坏「计数直读」），口径提示不承诺合计恒等 100%。
- **chip 全渲染的视觉密度**：本环境常态仅 2–4 桶非零，7+ 枚 0.00% 灰 chip 是「诚实但偏密」的取舍（行数稳定 + 全貌可见）；实机若确认过密，再评估「连续零桶折叠为 `其余 N 桶 0.00%`」单项。
