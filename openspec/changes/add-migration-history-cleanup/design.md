## Context

`ps_db_migration_log` 是操作元数据（`openspec/specs/database-management/spec.md` 既有语义：不参与数据迁移，目标库历史从零开始）。它与 `sys_audit_log` 的关系是判断"能否删除"的关键：

| | `ps_db_migration_log` | `sys_audit_log` |
|---|---|---|
| 内容 | 方向、源/目标、模式、表数、`backup_path`、`error_message`、耗时 | `action=migrate_database, resource=database` 一行摘要 |
| 写入时机 | 成功 / 失败（失败含超时、断连） | 与迁移日志同样成对写入 |
| 唯一事实源 | 否 | 是（审计） |

即：删除迁移历史行**不会**破坏审计链。

## Decisions

### D1：保留策略用「保留最近 N 条」，不用「按截止日期」

- 仓库对迁移备份已采用同款口径（`_cleanup_old_backups(keep=10)`），复用同一心智，无需用户理解"截止日期与记录时间的关系"
- 确定性更强：结果只取决于 N，不受记录时间分布影响
- 审计页的「按截止日期归档」之所以那样设计，是因为它删的就是审计本身、必须先导出留档；迁移历史不适用

### D2：不做 CSV 归档

迁移事件的审计已在 `sys_audit_log`。再导一份 CSV 属于重复留痕，且多出一个无人消费的产物（`data/archives/` 已有审计归档）。仅在 `backup_path` 指针上有信息损失，而备份 zip 本体仍在 `data/backups/`（保留 10 份），属可接受。

### D3：`running` 记录永不删除

模型允许 `status='running'`。当前代码只写 `success` / `failed`，但清理不能依赖"当前不会出现"这一事实——在 SQL 层加 `status != 'running'` 条件，单条删除同样保护。

### D4：删除作用域 = 当前活动库，且 UI 必须说明

切库后新库历史从零开始是既有 spec 语义；用户清理后切库会看到"又有一份"，因此弹窗内明确标注当前库名与作用域，避免误解为全局清理。

### D5：迁移进行中的互斥交给既有全局写锁

不新增并发控制。迁移运行时 `maintenance._migration_lock` 已让所有写请求返回 503，前端按普通请求错误提示即可（AGENTS.md #32：禁止在前后端造第二套并发控制）。

### D6：会话贯穿 `get_db`，不另开会话

按 AGENTS.md #29：审计钩子已在 `get_db` 会话上触发 autoflush（持 SQLite 写锁），service 必须接收并复用该会话，否则自锁超时。

### D7：单条删除只提供 API

表格已有 7 列且逐条删除对本场景（近百条批量噪声）无效；保留 API 以备后续按行操作接入主机的需求。

### D8：预览走独立只读端点，不由前端按已加载条数推算

列表接口固定 `limit(100)`，因此当库内记录超过 100 条时，前端拿到的条数小于真实总数——若用前端条数推算"将删除 N 条"，预览会在大数量下**静默说谎**。

两条路线里选了独立预览端点而非"把总数并进列表响应"：

- **不改既有响应形状**（`GET /database/history` 仍返回 `MigrationHistoryItem[]`），零兼容性破坏；改形状会连带改动既有后端测试与前端类型
- 预览与清理**共用同一判据函数** `_cleanup_scope(keep_last)`，从结构上消除"预览说删 4 条、实际删 3 条"的两处漂移（`running` 保护也在同一判据内）
- 只读 → 用 `GET` + 查询参数，不进审计、不占 `ROUTE_MAP` 的 mutating 映射

代价是打开弹窗多一次请求，可接受。

## Risks

- **误删导致"上次迁移是什么"无从查**：弹窗内实时预览删除/保留条数，默认保留 10 条，`N ≥ 现有条数` 时禁止提交。
- **审计噪声**：每次清理写一条审计记录，属预期留痕。
