## 一、用户项⑥：六个筛选下拉宽度不一致 + 「平铺」看不见（已定位根因）

### 1.1 实测（1600 视口，CSS 声明值 vs 实际渲染值）

| 控件 | CSS 声明 | 实际渲染 | 与「全部分组」差 |
|---|---|---|---|
| 搜索框 | 150 | **150** | — |
| 全部分组 | 140 | **113.5** | — |
| 全部集群 | 160 | **118.4** | +4.9 |
| 全部上游 | 160 | **128.3** | +14.8 |
| 全部插件 | 140 | **140** | +26.5（唯一带 `flex-shrink: 0`） |
| 全部状态 | 130 | **106.1** | −7.4 |
| 全部方法 | 130 | **106.1** | −7.4 |

六个下拉**渲染宽度全部不同**（113.5 / 118.4 / 128.3 / 140 / 106.1 / 106.1），根因不是 CSS 写错，而是：

> `.l5-toolbar` 是 `display:flex; flex-wrap:nowrap`，子元素默认 `flex-shrink: 1` —— 声明宽度只是「期望宽度」，空间不够时各控件**按内容宽度比例被压缩**，压缩量彼此不同。只有「全部插件」写了 `flex-shrink: 0` 所以保持 140。

### 1.2「平铺看不见」的根因（同一机制，更严重的受害者）

| 视口 | 卡片可用宽 | `.seg`（分组/平铺）渲染宽 | 其内部两个按钮实际占宽 | 结果 |
|---|---|---|---|---|
| 1600 | 1310 | 73.8 | 49 + 48 = 97 | 略挤，仍可见 |
| 1536 | 1246 | **64.2** | 97 | 边缘裁切 |
| 1440 | 1150 | **24.3** | 97 | 「平铺」被挤出 `.seg` 盒子 → **看不见** |
| 1366 | 1076 | **5.6** | 97 | 几乎完全不可见 |
| 1280 | 990 | **2.0** | 97 | 完全不可见（工具条另有 23px 溢出） |

`.seg` 没有任何 `flex-shrink: 0`，两个分段按钮是它的子元素不会跟着缩 —— 于是**段控被压扁到 2–24px，平面的 97px 内容溢出盒外**。这就是用户看到的「平铺已经看不见了」。

### 1.3 修法（无论「全部方法」去留都要做）

1. 六个筛选控件统一宽度 **104px**（= 全部分组当前目标宽，用户指定）+ `flex-shrink: 0`；
2. 右侧簇（计数 / 刷新 / 列配置 / 折叠 / 模式段）全部 `flex-shrink: 0`，**`.seg` 必须 shrink:0**（否则永远最先被压）；
3. `.l5-toolbar` 在超宽时 `flex-wrap: wrap`（第二行落右侧簇），保证任何视口都不压扁、不挤出。

### 1.4 统一 104 后的空间账（实测：注入 104px + shrink:0 后量 scrollWidth）

| 视口 | 卡片可用宽 | 保留「全部方法」 | **去掉「全部方法」（−110px）** |
|---|---|---|---|
| 1600 | 1310 | 0 溢出 ✓ | 0 溢出 ✓ |
| 1536 | 1246 | 0 溢出 ✓ | 0 溢出 ✓ |
| **1440** | 1150 | **溢 84px** ✗ | **0 溢出 ✓** |
| **1366** | 1076 | **溢 105px** ✗ | **0 溢出 ✓** |

只把搜索框收窄到 120 无效（`.l5-search` 外层宽度固定，输入框窄了外层不窄，实测溢出不减）。**即：1440/1366 这两档笔记本宽度，只有砍掉一个筛选控件才放得下** —— 这正是用户提议的方向。

## 二、讨论项：能否取消「全部方法」下拉，只保留第二行方法 chips

### 2.1 现状（设计与实现都有两套方法入口）

- 工具条「全部方法」下拉：`GET/POST/PUT/DELETE/PATCH/HEAD/OPTIONS/CONNECT/TRACE`（9 项）；
- 表头上方 chips 行：`全部 / GET / POST / PUT / DELETE / PATCH`（5 个高频 + 全部）；
- 两者**绑定同一个 `activeMethod`**（只是两个 UI），所以下拉实际只额外提供 `HEAD / OPTIONS / CONNECT / TRACE` 四个冷门方法。

### 2.2 冷门方法在真实数据里是否还有用（5 个集群全量 525 条路由）

| 方法 | 路由数 |
|---|---|
| （未设置方法，匹配全部） | 494 |
| GET | 31 |
| POST | 29 |
| DELETE | 26 |
| PUT | 25 |
| PATCH | 14 |
| **HEAD** | **14** |
| **OPTIONS** | **14** |
| **CONNECT** | **14** |
| **TRACE** | **14** |

→ 带方法的路由 153 条，其中 **56 条（37%）属于冷门四法**。直接砍掉下拉会让这 56 条**失去按方法筛选的入口**（不影响功能，只影响筛选体验）。OPTIONS 在真实场景里常见（CORS 预检），不能算纯噪声。

### 2.3 三个方案

| 方案 | 做法 | 省宽 | 能力损失 | 观感 |
|---|---|---|---|---|
| **B（推荐）** | 取消工具条下拉；chips 行尾部加「更多 ▾」小下拉承载四冷门方法（选中后按钮变为该方法的胶囊态并高亮） | 110px（工具条） | **0** | chips 行原本空着一大半（实测 chips 总宽 ≈380 / 1310），放一个「更多 ▾」毫无压力；工具条 1440/1366 单行放下 |
| C（用户原提议的直接版） | 取消工具条下拉，chips 保持 5 个高频 | 110px | 四冷门方法不可筛（56 条路由） | 最简洁，但能力有缺口 |
| D | 保留下拉，工具条允许换行 | 0 | 0 | 1440 起右侧簇掉到第二行，一行变两行 |

推荐 **B**：既拿到 110px 的空间收益（1440/1366 单行放下），又不丢 HEAD/OPTIONS 等筛选入口；chips 行的空间本来就在浪费。

## 四、拟入规格（批准后写入）

1. `list-page-console-visual` 增「工具条不压缩契约」：筛选控件 SHALL 固定宽度且 `flex-shrink: 0`；右侧操作簇（含模式段 `.seg`）SHALL `flex-shrink: 0`；超宽 SHALL 换行而非压扁。
2. 增「方法筛选入口」：高频方法以 chips 常驻（表头上方），冷门方法 SHALL 经 chips 行「更多 ▾」承载；工具条 SHALL NOT 再放「全部方法」下拉。
3. `mockup-parity-verification` 增「工具条宽度扫描」：至少 1600/1536/1440/1366 四档断言「无横向溢出 + `.seg` 宽度 ≥ 其内容宽」。

## 五、实施批次（批准后）
