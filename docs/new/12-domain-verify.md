# 12. 绑定域名与全链路验证

> 本章场景：搭建主线所需的全部资源已经就绪——路由与上游（第 7~8 章）、证书（第 9 章）、四层与 DNS 监听（第 3、10~11 章）。本章把域名 `test.com` 指向网关节点，让 HTTPS 链路真正跑通业务请求，然后一次性验证 **HTTPS(5000) / TCP(8880) / UDP-DNS(53)** 三条链路。这是从零搭建主线的收官章。

# 域名解析准备（本机操作）

> ⚠️ 本节操作发生在**你自己的电脑**上，不是磐石 Admin 平台界面上的操作。

服务器证书 `test.com` 已经发布到节点（第 9 章），但你的电脑还不知道 `test.com` 对应哪台机器。演示环境没有配置 DNS 服务器，用本机 hosts 文件模拟解析：

**Windows**（以管理员身份运行记事本打开）：

```text
notepad C:\Windows\System32\drivers\etc\hosts
```

在文件末尾追加一行后保存：

```text
192.168.0.13 test.com
```

**Linux / macOS**：

```bash
sudo sh -c 'echo "192.168.0.13 test.com" >> /etc/hosts'
```

验证解析是否生效：

```bash
ping -c 1 test.com        # Windows 用: ping -n 1 test.com
```

预期输出中 `test.com` 解析到 `192.168.0.13`。

# 为 HTTPS 调整路由匹配端口

第 8 章创建的「API路由」使用高级匹配 `server_port == 16610`（HTTP 端口）；而 HTTPS 监听在第 3 章开在了 **5000**。要让 `https://test.com:5000/api/*` 命中路由，需要把匹配端口改为 5000：

1. 点击左侧侧边栏：【核心功能】→【路由管理】，找到「API路由」，点击【编辑】。
2. 切换到【高级匹配】标签页，把匹配值从 `16610` 改为 `5000`：

   ![修改匹配端口](images/12-01-route-port-5000.png)

3. 点击【保存】，回到列表点击【发布】并勾选节点 `.13`（流程与第 3 章 3.3 相同；若失败，回到[第 3 章 3.4 发布失败排查](03-edge-env.md)处理）。
4. 发布成功后，路由版本号从 v1 变为 **v2**。

# 全链路验证

三条链路逐条验证。以下命令都在**你的电脑**（能连通 192.168.0.13 的机器）上执行。

## ① HTTPS 七层链路（端口 5000）

```bash
curl -vk https://test.com:5000/api/ping
```

检查输出中的三个关键点：

| 检查点 | 预期 |
|---|---|
| TLS 握手 | `SSL connection using ...` 表示握手成功 |
| 证书主体 | `subject: CN=test.com`（第 9 章签发的服务器证书，经 SNI 自动选择） |
| 业务响应 | HTTP 状态码 + 来自「本地测试服务」的响应内容 |

> 💡 `-k` 表示跳过证书链校验——因为 test.com 由我们自建的根证书签发，系统信任库里没有它。要完整校验，可把第 9 章的根证书导入系统信任库（或浏览器），之后去掉 `-k` 也能通过校验。生产环境应使用公信 CA 签发的证书，无需此步骤。

## ② TCP 四层链路（端口 8880）

```bash
timeout 3 bash -c 'cat < /dev/null > /dev/tcp/192.168.0.13/8880' && echo "TCP 8880 通"
```

预期输出 `TCP 8880 通`（第 10 章的四层代理监听）。

## ③ UDP/DNS 链路（端口 53）

```bash
dig @192.168.0.13 -p 53 test.com +short
```

预期返回节点 IP（第 11 章 DNS 代理的一致性哈希结果，同一客户端多次查询稳定）。

## 验证结果汇总

| 链路 | 命令关键点 | 依赖章节 |
|---|---|---|
| HTTPS :5000 | 证书 CN=test.com + `/api/*` 业务响应 | 3（监听）+ 8（路由）+ 9（证书） |
| TCP :8880 | 端口连通 | 3 + 10 |
| UDP :53 | dig 返回解析结果 | 3 + 11 |

# 排错速查

| 现象 | 处理 |
|---|---|
| ping test.com 不通 | hosts 未生效：检查是否以管理员/root 保存、有无拼写错误；浏览器需清 DNS 缓存（`ipconfig /flushdns`） |
| HTTPS 报 `Connection refused` | 第 3 章的 5000 监听未发布到 .13：回第 3 章重新发布 edge.env |
| HTTPS 握手失败但端口通 | 确认证书已发布（第 9 章卡片为「已发布」状态）且集群一致 |
| HTTPS 返回 404 | 路由匹配端口未改为 5000，或未重新发布（本章第二节） |
| TCP/DNS 不通 | 回第 10/11 章核对代理配置与发布状态 |

# 本章小结

- hosts 模拟了演示环境的域名解析；生产环境由真实 DNS 承担同样职责
- 「编辑资源 → 重新发布 → 版本递增」是通用的变更流程（本章路由 v1 → v2）
- 三条链路验证命令：`curl -vk https://test.com:5000/api/ping`、`/dev/tcp/192.168.0.13/8880`、`dig @192.168.0.13 -p 53 test.com`
- 至此，一套可用网关搭建完成：HTTP(S) 七层、TCP 四层、UDP/DNS 全部就绪
