## 1. 主要问题清单（按严重度）

### P0 —— 反馈失真 / spec 契约违规

**P0-1 失败没有原因，用户只能看到「失败」**
`install_task_node.stderr` 只在一种情况下有中文归因：ansible 退出码为 0 但输出命中「no hosts matched / unreachable / permission denied」（`ansible_service._ansible_false_success_error`，`ansible_service.py:1235`；`node_task_service.py:341` **两处都包在 `if rc == 0` 内**）。真实失败大多是 rc≠0：实机任务 #11 两节点 `rc=4`、`stderr` 为空、无日志文件，用户在列表看到「失败」，点详情看到「失败 / rc 4 / 耗时 11s」，展开日志只有英文 ansible traceback 与 ANSI 色码。**这是本模块最影响信任的问题**：运维拿到「失败」却拿不到下一步该做什么。
反面样板同期存在（任务 #10 的中文归因文案质量很好），说明能力已有、只是没覆盖到 rc≠0 与任务级汇。

**P0-2 计数与实际子项不一致，列表出现物理不可能的数字**
`total/success/failed_nodes` 在收尾时由 `results.count(...)` 写入（`node_task_service.py:365-367`），但 `total_nodes` 只在创建时取一次 `len(node_ids)`（:117）。历史任务 1/2/3 因此显示 `2/1 成功`、`1/1 成功` 却状态「部分成功」。前端进度条按 `success/total` 计算（`NodeTaskCenter.vue:1681-1684`），比例 >100% 时进度条画满、标签写「部分成功」，**三个字段互相打架**，用户第一反应是「系统坏了」。

**P0-3 六类任务的「取消」是空操作**
spec「取消与并发保护」要求「任一任务类型处于 running 时用户 SHALL 可取消」。实现里 `cancel_event` 只传给 install/upgrade/edge_pack/edge_env/distribute（`node_task_service.py:549-615、695`）；`nginx_cmd`（start/stop/reload/check）、`statistic`（:452-459）、`software_check`（:468）、脚本模式 cmd_exec（:470-526）**完全不消费取消事件**。但行菜单对所有 pending/running 任务都渲染「取消」（`NodeTaskCenter.vue:81-86`）。用户点取消 → toast「任务取消已发起」→ 状态仍是「执行中」→ 最终变成「失败」或「成功」。**按钮承诺了系统做不到的事**，且这条链路在 spec 里是明确要求的。

**P0-4 取消后的状态不落地：`cancelled_nodes` 恒为 0**
子项状态机只有 pending/running/success/failed/skipped（`node_task_service.py:298/304/355`），「cancelled」从未写入任何子项，于是 `results.count("cancelled")` 恒为 0（:367）。实机任务全部显示「取消: 0」，即使是被取消的任务。用户无从区分「取消成功」与「取消没生效」。同时 DB 没有任何「取消已请求」的持久化标记（只在内存 Event），刷新页面后「取消中」这个中间态消失。

**P0-5 进程重启中断的任务没有原因**
spec「进程重启后任务状态处理」要求标记为 failed **且带「进程重启中断」标记**；实现只把 pending/running 改成 failed（`node_task_service.py:952-962`），不写 stderr、不写详情，前端看到的是又一个「无原因失败」。

### P1 —— 易用性 / 信息层级 / 一致性

**P1-1 全局列表没有「集群」列**
`GET /node-tasks` 跨集群返回（`:558`），列表 9 列里没有集群（`NodeTaskCenter.vue:1602-1612`）。多集群平台上，用户看到「命令执行 / 部分成功 / 4 节点」却不知道这是哪个集群的任务，必须点开才可能知道（详情里也没有集群字段）。

**P1-2 没有操作人**
`NodeTask.created_by` 列存在、`create_task(created_by=...)` 形参存在，但端点从不传（`node_tasks.py:479-486`）→ API 恒返回 `null`。生产环境多人共用平台时，任务列表无法回答「这是谁跑的」。审计表有记录，但任务中心取不到。

**P1-3 状态 / 节点 / 进度三列表达同一件事，且「节点」名不副实**
「状态」（部分成功）+「节点」（`1/4 成功`）+「进度」（条）占掉表中最贵的 300px；而详情里同样叫「节点」的列显示的是 `10.99.99.3 /edge`。**同名不同义**，是本页最误导的一处命名。

**P1-4 进度条把「失败」画成「未开始」**
进度条 `progressPercent = success_nodes/total_nodes`（:1681-1684）：失败任务 success=0 → 空条（看起来像待执行）；部分成功 → 暗红条，与「失败」的红色色相过近（视觉评审 A/C 段）。**没有一个视觉元素表达「失败了 3 台」。**

**P1-5 查看失败原因的路径长达 4 层**
列表 → 详情弹窗 → 节点行「展开」→ 日志查看器「stderr」页签。而「展开」依赖 SSE/文件回放，`statistic`/`start` 等类型根本不产生日志（`log_file=null`），展开后是「无输出」——**用户走了 4 步，得到空面板**，且没有任何文案解释「该任务类型不产生实时日志」。

**P1-6 详情弹窗信息组织失序**
无任务 ID/创建时间/结束时间/耗时（列表有、详情没有，点开反而丢上下文）；`参数:{ "cmd": "whoami", … }` 原样 JSON 裸露 4 行、无等宽字体、无复制；`rc` 列是开发者语汇；每节点两个等价按钮「展开」「完整日志」语义边界不明；「重试失败节点」与「关闭」同级同样式，真正的下一步操作没有主次。

**P1-7 日志无法下载 / 导出**
`GET /node-tasks/{id}/items/{node_id}/log` 返回 `text/plain` 正文，无 `Content-Disposition`、无 range、无多节点打包、无整任务导出（`node_tasks.py:747`）。排障时用户只能选中复制，长日志需手工滚动。同时日志文件**没有行数上限**（`ansible_service.MAX_LOG_LINES=500` 定义后全仓无引用），设计文档 node-task-center.md:64 写的「每节点最多保留 500 行」未生效 → 长跑任务日志无限增长。

**P1-8 创建表单缺必填标识与关键说明**
12 个字段无一处 `*`；必填性只体现为「创建按钮 disabled」+ 提交时一句合并提示「请选择集群、节点和操作类型」（一次性报三个字段，难定位）；「黑名单 / 白名单 / 不限制」三个 radio **没有组标签**，用户不知道它在约束什么；帮助文案「任务参数将从节点记录自动读取（安装路径/管理端口等）」在命令执行表单里同样出现（对命令执行毫无意义且误导）；命令输入框无「复制」入口（脚本模式反而有「转换为命令」）。

**P1-9 切换集群后安装包 / 版本列表不再刷新（功能性缺陷）**
`onTaskTypeChange` 才真正请求列表（:2120-2135），而 `watch(createClusterId)` 只清空不重拉（:2138-2145）。因此「先选类型（安装 OpenResty / 升级传包）→ 再换集群」后，对应下拉恒为空，必须切走类型再切回才恢复。用户看到的是「这个集群没有安装包」。

**P1-10 重试会抹掉上一次的执行证据**
`retry` 重置子项时清空 rc/stdout/stderr/command 并删除该节点日志文件（`node_task_service.py:389-416`）。重试后无法回看上次为什么失败，交接/复盘时证据消失。前端确认弹窗也未提示「上次执行日志将被清空」。

**P1-11 重试无终态前置校验**
端点不校验任务状态，对 running 任务调用会再起一次 `_execute` 覆盖 `_running[task_id]`（`node_tasks.py:605`）；也不校验 `node_ids` 是否属于该任务（不匹配则静默无操作）。

**P1-12 列表无搜索、无时间范围、无集群过滤**
只有状态下拉 + 类型下拉（:16-32）。spec 明确要求「可按状态/类型/时间筛选」，时间维度未实现。全局搜索（顶栏 Ctrl K）不是本页的替代品——它不认任务 ID 之外的语义。

**P1-13 文件入口抢占主行动，术语自造**
页头三个等权按钮：「待用上传（0）」「任务留档（0）」「＋ 新建任务」。前两个是低频维护视图，却与主 CTA 同排同尺寸；「待用」「留档」不是用户词汇（弹窗内又分别叫「选择已上传文件」「源文件副本」，三套说法）。两者都是 `modal-overlay` 弹窗而非视图切换。

**P1-14 状态标签两套实现、三种呈现**
列表是手写 `<span class="status-tag">`（:2258-2288），详情节点表是另一套 `<span class="ner-status">`，详情顶部「状态: 部分成功」是纯黑文本。同一语义三种视觉，且全站其他页面用 `a-tag`。

**P1-15 空态缺失**
主表依赖 AntDV 默认「暂无数据」，没有引导文案与主行动；两个文件弹窗各自手写空态（:290-300、:411-413）——同一页两套空态标准。

### P2 —— 打磨项（本轮不做，记待办）

- 任务无名称/备注字段：只能靠 `#id + 类型 + 时间` 认任务，「昨天那次升级」无法表达。
- 无任务模板/最近使用：高频的同类任务每次重填参数。
- 无批量重试、无结果导出（CSV/Excel）。
- SSE 事件无时间戳、无序号、无 level，重连回放与增量无去重键。
- `duration` 无独立字段，子项 `started_at` 含信号量排队时间（不是纯执行耗时）。
- 12 vs 14 任务类型：后端有 `check`、`edge_env_deploy`，前端建不出来（`check` 与 `statistic` 命名还分叉）。
- 前端 12 类任务全塞一个下拉，无分组。
- 「任务留档」只能全量拉取后前端过滤（无按任务查询端点）。
- 行勾选无批量工具条，勾选能力悬空。

## 2. 信息架构优化建议

### 2.1 现状结构（单页 + 5 个弹窗）

```
页头：待用上传(N) | 任务留档(N) | ＋新建任务
筛选：状态▾  类型▾  [批量删除]  刷新
表格：ID|任务类型|状态|节点|进度|创建时间|结束时间|耗时|操作
弹窗：详情 / 待用上传 / 任务留档 / 创建任务
```

问题：三种性质的东西（**视图入口**、**文件管理**、**主行动**）挤在同一行；任务详情是 900px 弹窗，但里面要装「元信息 + 节点结果 + 日志 + 软件矩阵」四类内容，宽度不够只能靠行内展开层层套。

### 2.2 建议结构

**a. 页面主体保留「任务列表」，详情升级为独立路由页 `/node-tasks/:id`（推荐）**

理由：日志是排障主战场，需要全宽 + 可滚动 + 可复制 + 可分享链接；弹窗形态下「详情里再展开日志」被迫做了三层。路由化后浏览器后退、刷新保留、URL 可直接发给同事。列表页保留「快速预览」也非必需——跳转只多一次点击。

> 备选（成本更低）：保留弹窗，内部重排为「meta 行 + 四格状态卡 + 节点结果表 + 日志抽屉」，并把「展开 / 完整日志」合并为「查看日志」打开右侧抽屉。适合本轮不做路由改造时采用。

**b. 文件类入口降级**

「待用上传 → **暂存文件**」「任务留档 → **任务源文件**」，从页头移到列表工具栏右端的次按钮组（text/ghost 样式）；页头只保留「＋ 新建任务」为唯一主行动。若后续文件量变大，再升级为页面顶部的视图切换（任务 / 文件），而非弹窗。

**c. 列表列重排（9 列 → 8 列，信息密度提升）**

| 现状 | 建议 | 说明 |
|---|---|---|
| ID | `#` 序号列（全站统一解剖）+ 任务号 tooltip | 对齐 AGENTS #59 |
| 任务类型 | 保留，label 统一（「Reload」→「重载（Reload）」） | |
| 状态 | 与「节点」「进度」合并为 **「结果」** 单元格 | 状态 chip + 计数 + 分段条 |
| 节点（1/4 成功） | 并入「结果」 | 消除同名不同义 |
| 进度（条） | 并入「结果」，改为分段条 | 见 §6 |
| —— | **新增：集群** | 全局列表必需 |
| —— | **新增：失败原因**（截断 + tooltip + 首条归因） | P0-1 的呈现位 |
| 创建时间 / 结束时间 / 耗时 | 合并为「时间」列：结束时间 + 耗时（创建时间进 tooltip） | 两列 19 字符几乎相同，扫描收益低 |
| 操作 | 保留「详情」，次操作收进 `⋯`；执行中行直出「取消」 | |

**d. 筛选条补齐**：搜索（任务号 / 节点 IP / 命令关键字）、集群、任务类型（分组下拉）、状态、时间范围；右侧常驻「共 N 条」。批量操作工具条在勾选后出现（重试 / 删除 / 导出）。

**e. 详情页分区（自上而下：结论 → 细节 → 证据）**

```
面包屑：节点任务 / #11
① 结论层：状态 chip + 计数摘要 + 失败原因摘要 + [重试失败节点(3)]
② 上下文层：任务号 · 类型 · 集群 · 发起人 · 创建/开始/结束 · 耗时
③ 节点层：节点表（可搜索/按状态过滤）+ 每行「查看日志」
④ 参数层：可读 key-value + 折叠「原始参数」+ 复制
⑤ 证据层：日志抽屉（stdout/stderr/命令/实时，支持下载与整任务导出）
```

## 3. 关键页面模块布局建议

### 3.1 列表页

```
┌ 节点任务 ────────────────────────────────────────────────────────────┐
│ 查看并管理各集群的节点运维任务                     [＋ 新建任务]     │
│                                    刷新 · 暂存文件(3) · 任务源文件(7)│
├──────────────────────────────────────────────────────────────────────┤
│ 🔍 任务号 / 节点 IP / 命令   [集群 ▾] [类型 ▾] [状态 ▾] [近 7 天 ▾] │
│                                                    共 128 条        │
├──┬──────────┬──────┬─────────────────────────────┬────────────┬─────┤
│# │ 任务类型  │ 集群 │ 结果                         │ 时间       │操作 │
├──┼──────────┼──────┼─────────────────────────────┼────────────┼─────┤
│11│ 状态查询  │ test │ ⚠ 部分成功  ●●○○ 1 成 3 败  │ 11-01 17s  │详情 │
│  │          │      │ ⚠ 3 台节点不在主机清单       │            │     │
├──┼──────────┼──────┼─────────────────────────────┼────────────┼─────┤
│10│ 命令执行  │ test │ ✓ 成功      ●●●● 4/4        │ 08-10 17s  │详情 │
└──┴──────────┴──────┴─────────────────────────────┴────────────┴─────┘
                                          共 128 条  ‹ 1 2 3 ›  20/页
```

要点：结果单元格一行给「状态 + 计数 + 分段条」，第二行给失败归因（仅失败/部分成功时出现）；失败归因最多 1 行省略，hover 显示完整；颜色只保留「失败红 / 部分成功琥珀 / 执行中蓝」，其余中性。

### 3.2 详情页（推荐形态）

```
┌ 节点任务 / #11 ──────────────────────────────────────────────────────┐
│ ⚠ 部分成功   成功 1 · 失败 3 · 跳过 0 / 共 4      [重试 3 台失败节点]│
│ 状态查询 · 集群 test · 发起人 admin · 用时 11s                       │
│ ⚠ 失败原因：3 台节点不在 Ansible 主机清单；1 台 SSH 连接超时          │
│   → 处理建议：检查 inventory/host 中是否存在该节点        [查看详情] │
├ 节点结果 ────────────────────────────────────────────────────────────┤
│ 🔍 节点 IP        [状态 ▾]                       [导出结果]          │
│ IP            状态    耗时   失败原因                操作            │
│ 192.168.0.14  失败    11s    无法连接（SSH 超时）    查看日志         │
│ 192.168.0.13  成功    10s    —                       查看日志         │
├ 任务参数 ────────────────────────────────────────────────────────────┤
│ 执行命令  whoami        执行策略  白名单        超时  30 秒  [复制]  │
│ ▸ 原始参数（JSON）                                                    │
└──────────────────────────────────────────────────────────────────────┘
```

要点：① 结论置顶，用户不滚动就知道「成没成、为什么、下一步做什么」；② 参数变成人话，JSON 收进折叠块；③ 「查看日志」是每行唯一入口，打开右侧抽屉（stdout/stderr/命令/实时四页签 + 下载）。

```
┌ 创建节点任务 ─────────────────────────────────────────────────────────┐
│ ① 目标  集群* [test ▾]      ② 节点* [🔍 搜索]  全选 | 清空           │
```

## 6. 状态展示优化建议

1. **分段进度条取代单一百分比条**：绿=成功、红=失败、灰=跳过、条纹=执行中。失败任务不再呈现「空条」。
2. **计数口径统一**：以子项实际记录为准（`成功 x / 失败 y / 跳过 z / 共 n`），杜绝 `2/1` 这类不可能数字；比例 >100% 时以子项为准并告警日志。
3. **状态 chip 单组件**：列表 / 详情 / 节点行共用一套（可直接用 `a-tag` 或统一 `status-tag`），色相与图标区分「失败（红 + ✕）」「部分成功（琥珀 + ⚠）」「执行中（蓝 + 转圈）」「取消（灰 + ⊘）」——**靠形状而非纯色**，解决 12px 淡底红/橙难分辨。
4. **补「取消中」中间态**：`cancel_requested_at` 落库，chip 显示「取消中」，刷新后仍在；取消完成后转「已取消（已停止 3 / 已完成 1）」。
5. **执行中展示时间语义**：`已运行 12s · 2 台执行中 · 2 台排队`，而不是只显示「执行中」。
6. **终态任务给时间线**：创建 → 开始 → 结束（含各节点），失败节点标红，回答「卡在哪一步」。

## 11. 实施记录（2026-11-01 当日，随 `openspec/changes/node-task-ux-optimization` 落地）

### 11.1 三个 P0 的闭环（实机证据）

| 问题 | 修前（实测） | 修后（实测） |
|---|---|---|
| 失败无原因 | 任务 #11：`rc=4`、`stderr` 空、`log_file=null`，真因（`ssh: connect ... timed out`）只在 stdout 英文 + ANSI 里 | 任务 #12：`failure_reason` = 「节点 10.99.99.3 不在 Ansible 主机清单中，请在 inventory/host 文件中添加该节点的 SSH 连接信息」，`failure_summary` = 「1 台节点不在 Ansible 主机清单中」 |
| 计数失真（`2/1 成功`） | 历史任务 #1/#2/#3 主表 `total_nodes=1`、子项 3 条 | 启动 `backfill_task_stats()` 按子项重算 → 3/3/…，界面不再出现物理不可能的口径 |
| 取消是空操作 | 点取消后 DB 标 `cancelled`，但 `ansible-playbook` 与节点上 `sleep 45` **跑到自然结束**（约 45s） | 取消后 **+0.5s** `pgrep -fc '[a]nsible-playbook'` 由 2 → 0；远端 `ps` 确认 `sleep` 已中断 |

### 11.2 实施中发现、评审时未预见的三个真问题

1. **归因优先级会把人带偏**：ansible 的 SSH 认证失败是包在 `UNREACHABLE!` 里的（`Failed to connect to the host via ssh: ... Permission denied`），同时命中「不可达」与「认证失败」两个标记。原优先级把「无法连接」排在前面 → 用户被告知「检查网络与 SSH 服务」，而真正要改的是清单里的密码/密钥。已把认证失败提到第 2 位，并加两条钉死测试。
2. **只改 `cancel_callback` 杀不掉 ansible 腿**：ansible-runner 用 `child.expect(timeout=5)` 读输出，**命令静默期内根本不轮询回调**，实测取消后 +4s 仍有 2 个进程。必须另起 `cancel_event` watcher 直接按标记 `killpg`（`panshi_run_token` 精确匹配，避免误杀并发任务）。
3. **重试会让任务「永久取消中」**：`_cancel_flags[task_id]` 里那个已 `set()` 的 Event 未在重试时替换，新一次执行立刻被判「已取消」。重试必须换新 Event + 清 `cancel_requested_at`。同时 `cancel_task` 对终态任务应幂等无副作用（不再给已结束任务挂「取消中」）。

### 11.3 与评审建议的偏离（有意）

| 评审建议 | 实际做法 | 理由 |
|---|---|---|
| 日志上限沿用 500 行 | **5000 行** | 500 对 `install_openresty` 的编译输出过少，会截掉关键报错 |
| 重试时在日志里追加「第 N 次执行」分隔头 | 整份留档改名 `{node_id}.attempt{N}.log`，活动日志保持空文件 | 「本次输出」语义干净，历史证据（输出 + 失败原因）完整可经 `?attempt=N` 回看 |
